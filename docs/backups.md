# Резервні копії бойової бази

Блок B7a (див. [PLAN.md](PLAN.md)). Рішення D30 у [decisions.md](decisions.md). Статус: пропозиція Claude, чекає підтвердження розробника.

## Навіщо

Безкоштовний Supabase не робить резервних копій: його власна документація радить таким проєктам самим регулярно експортувати дані. У базі лежать клієнти, замовлення, ціни й борги по боксах. Без копії одна помилкова міграція, випадкове видалення або збій проєкту означають втрату всього. Тому копії робимо самі, і вони мають бути готові **до того, як у бойову базу потраплять справжні дані** (до B7).

## Кілька слів, які зустрінуться

| Слово | Що це |
|---|---|
| Дамп | Файл, у якому збережено вміст бази. З нього базу можна відновити |
| `pg_dump` | Стандартна програма Postgres, що робить дамп |
| GitHub Actions | Безкоштовний планувальник GitHub: запускає наш скрипт щоночі |
| `age` | Невелика програма шифрування. Шифрує дамп публічним ключем, розшифрувати можна лише приватним |
| Cloudflare R2 | Сховище файлів. Безкоштовно 10 ГБ, передача даних назовні безкоштовна |
| Відновлення | Підняти нову базу з дампа, якщо стара пропала |

## Що копіюємо і що ні

| Що | Копіюємо | Чому |
|---|---|---|
| Дані схеми `public`: клієнти, замовлення, ціни, журнал змін, довідники, лічильники номерів | Так | Це і є робота компанії |
| Акаунти `auth.users` і `auth.identities` | Так | Щоб після відновлення працівники мали ті самі логіни, паролі й прив'язку до Google |
| Структура таблиць | Ні | Вона в репозиторії (папка `drizzle/`), відновлюється командою `npm run db:migrate` |
| Налаштування Supabase Auth: Google Client ID і Secret, вимкнена реєстрація, Redirect URLs | Ні | Не входять у дамп бази. Налаштовуємо заново за README |
| Файли в Supabase Storage (щоденна вигрузка в Excel) | Ні | Вигрузка створюється щоночі наново |
| Ключі й секрети | Ніколи | Вони лише у Vercel, GitHub Secrets і менеджері паролів |

## Схема

```
Supabase (бойова база)
      │  щоночі, GitHub Actions
      ▼
pg_dump ► стиснення ► шифрування (age) ► Cloudflare R2 (акаунт Романа)
                                              │
                                              ▼
                        перевірка свіжості: копія старша за 36 годин ► сповіщення
```

**Чому саме так**

- **GitHub Actions**, а не Vercel: програми `pg_dump` на Vercel немає, а функція там живе обмежений час. GitHub Actions безкоштовні для публічного репозиторію.
- **Шифрування обов'язкове:** репозиторій публічний, а в копії є персональні дані клієнтів (ТЗ: вони мають лежати лише в акаунтах замовника). Копія без ключа нічого не відкриє, навіть якщо хтось дістанеться до сховища.
- **Сховище в акаунті Романа**, не в нашому: дані належать компанії.
- **Окремо від Supabase**, інакше втрата проєкту забере разом із собою і копії.

## Деталі налаштування

- **Розклад.** Щодня о 01:17 за UTC (приблизно 03:17–04:17 за Києвом). Саме хвилина «17», а не «00»: на початку години GitHub перевантажений, і запуски можуть запізнюватись. Запуск вручну (`workflow_dispatch`) ми робимо **перед кожною міграцією бойової бази**.
- **Підключення.** Через Session pooler: прямий доступ до бази працює лише по IPv6, а в GitHub-раннерів його немає. Версія `pg_dump` 17, така сама, як на сервері.
- **Що дампимо.** Дані (без структури) схеми `public` та таблиці `auth.users`, `auth.identities`, у стиснутому вигляді.
- **Шифрування.** `age` публічним ключем. Приватний ключ є лише в менеджерах паролів Романа і розробника, у GitHub його немає.
- **Зберігання.** Бакет у R2. Щоденні копії зберігаємо 30 днів, перші копії місяця 12 місяців (правила життєвого циклу бакета). Розмір дампа поки порядку мегабайтів (3,5 тисячі замовлень), перевіримо на першому запуску. R2 безкоштовно дає 10 ГБ.
- **Секрети в GitHub** (Settings, Secrets): рядок підключення, публічний ключ `age`, ключ доступу до R2 (лише на запис у цей бакет, якщо сховище дозволяє). У коді репозиторію секретів немає.
- **Скрипт у репозиторії**, не лише в налаштуваннях GitHub: `scripts/backup.sh` і `.github/workflows/backup.yml`, щоб усе можна було перевірити й відтворити.

## Моніторинг: копія, про яку ніхто не знає, не копія

| Що може зламатись | Як помітимо |
|---|---|
| Запуск завершився помилкою | Лист від GitHub на власника репозиторію |
| GitHub тихо вимкнув розклад | У **публічному** репозиторії розклад вимикається після 60 днів без активності в ньому (офіційна документація GitHub). Тому не покладаємось на листи: окремо перевіряємо дату останнього файлу в бакеті |
| Файл порожній або занадто малий | Скрипт перевіряє розмір і падає, якщо менший за поріг |
| База призупинилась (Free) | Скрипт не зможе підключитись і впаде. Тоді проєкт треба відновити в кабінеті Supabase |

**Перевірка свіжості.** Раз на добу кінцева точка CRM дивиться дату найновішого файлу в бакеті. Якщо вона старша за 36 годин, власник отримує повідомлення в Telegram (коли бот з'явиться). До того часу розробник раз на місяць відкриває вкладку Actions у GitHub і бакет, і перевіряє, що копії є.

## Як відновити

Орієнтовно 1–2 години. Дані втрачаються до моменту останньої копії (до 24 годин).

| # | Хто | Крок |
|---|---|---|
| 1 | Розробник | Створити новий безкоштовний проєкт Supabase (Франкфурт) в організації замовника. Якщо слот зайнятий, старий проєкт видалити або призупинити |
| 2 | Claude | Застосувати структуру: `npm run db:migrate` з рядком підключення нового проєкту |
| 3 | Розробник | Розшифрувати останню копію приватним ключем `age` |
| 4 | Claude | Завантажити дані: спершу `auth`, потім `public`, у транзакції з вимкненими тригерами (`SET session_replication_role = replica`), щоб журнал змін і історія статусів не задвоїлись. Так само радить документація Supabase |
| 5 | Claude | Перевірити: кількість клієнтів і замовлень, найбільший номер замовлення, вхід власника |
| 6 | Розробник | Заново налаштувати Supabase Auth за README: вимкнути реєстрацію, увімкнути Google, додати Redirect URLs |
| 7 | Розробник | У Google Cloud змінити адресу повернення на адресу нового проєкту Supabase (вона містить ідентифікатор проєкту) |
| 8 | Розробник | У Vercel замінити чотири змінні Production і перезапустити деплой |

## Пробне відновлення (обов'язково до B7)

Копія, яку жодного разу не відновлювали, може виявитися непридатною. До першої бойової міграції:

1. Створити тимчасовий безкоштовний проєкт **в організації замовника** (другий слот, поряд з `icelab-prod`). Не в організації розробника: у копії персональні дані клієнтів.
2. Пройти кроки відновлення вище.
3. Видалити тимчасовий проєкт, зафіксувати час і проблеми.

Далі раз на квартал, а також після зміни схеми бази.

## Якщо колись купимо Supabase Pro

На платному плані є щоденні копії за 7 днів (за потреби окремо додається відновлення на момент часу). Наші власні копії тоді лишаються додатковим страхуванням в іншому сховищі, їх можна не прибирати.

## Що нам невідомо і треба перевірити

- Чи потрібна картка при створенні акаунта в Cloudflare R2.
- Фактичний розмір дампа на справжніх даних.
- Що саме треба з таблиць `auth` для коректного входу після відновлення: перевіряємо на пробному відновленні.
