# B0. Старт проєкту

Частина загального плану: [PLAN.md](../PLAN.md). Розмір: S.

## Мета

Мати працюючий «скелет»: репозиторій з перевіреним CI, три середовища (dev, staging, prod), підключені Vercel і Supabase, і відправлені питання замовнику. Після B0 можна одразу починати схему БД (B1) без організаційних зупинок.

## Ролі в плані

| Позначка | Хто |
|---|---|
| **Claude** | пише код і конфігурацію, запускає команди локально, перевіряє результат |
| **Розробник** | створює акаунти, вносить ключі і паролі, надсилає повідомлення замовнику, ухвалює рішення |
| **Роман** | замовник: акаунти компанії, оплата, DNS, відповіді на питання |

Межі, які не змінюються: Claude не створює акаунти, не вносить паролі й ключі в жодні поля, не читає вміст `.env.local` і не платить. Усі секрети лише у змінних середовища Vercel і в менеджері паролів розробника.

## Критерії готовності B0

1. `npm install && npm run dev` запускає застосунок локально на dev-базі; `/api/health` повертає `db: ok`.
2. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` проходять локально і в GitHub Actions.
3. Кожен PR збирає preview на Vercel, який працює зі staging-базою; `main` деплоїться в production з prod-базою; `/api/health` у обох повертає `db: ok`.
4. У репозиторії немає секретів, `.env.example` описує всі змінні з ТЗ, секрети лише у Vercel.
5. README описує запуск, середовища, змінні й деплой; `docs/decisions.md` містить D1–D9.
6. Створено `docs/decisions.md` з рішеннями D1–D9. Питання Роману за рішенням розробника відкладено до блоків, яким потрібні відповіді.
7. `main` захищений: зміни лише через PR із зеленим CI.

## Ризики

- **Node 26 щойно став LTS** (жовтень 2026). Next.js 16.4.5 на ньому перевірено, але нові залежності можуть мати свої нюанси; запасний варіант — Node 24 (його теж підтримує Vercel).
- **Dev-база в хмарі.** Безкоштовний проєкт Supabase без бекапів; він засинає після тижня без активності (його треба розбудити в панелі Supabase). У безкоштовній організації два слоти: у розробника dev і за потреби staging, а `icelab-prod` створюємо в організації замовника (D28). Скидання dev-бази робитимемо лише захищеним скриптом, який відмовляється працювати поза dev.
- **Репозиторій публічний** (рішення розробника лишити так). Секретів у коді немає, але код і `docs/` (бізнес-правила клієнта) видно всім. Тому в документах і коміттях не зберігаємо ключі та персональні дані клієнтів. Захист `main` без прав Admin розробник налаштувати не може.
- **Безкоштовні плани (D28).** Vercel Hobby за умовами лише для некомерційного використання (ризик прийняв замовник), а безкоштовний Supabase не робить резервних копій. Заходи: D29 і D30 у `docs/decisions.md`, [backups.md](../backups.md).
- **Відповіді Романа** можуть прийти не одразу. B1–B3 від них майже не залежать (виняток — питання 4 для B2), тому очікування не зупиняє роботу.
